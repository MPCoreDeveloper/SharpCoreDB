## 2. Highlights of the v2.1 line

### 2.1 Storage and write path

- **The fixed-width inline capacity now ships at 16 by default on both storage paths.**
  `DatabaseConfig.FixedWidthInlineValueBytes = 16` (was 0). A short String/Blob value is written
  into the record slot instead of the overflow arena, so a fixed-width record stops paying an arena
  write for every variable-length value. Measured on the batched multi-row shape (1,000
  rows/statement, median of 5): **62,545 → 70,145–74,634 rows/s (+12 % to +19 %)**, 4,943 → 4,348 B
  allocated per row, and the overflow arena **halved** (1,006,670 → 488,890 B). The cost is space:
  each variable-length column reserves `2 + 16` bytes, so that schema's table file grew 2.4×
  (760,000 → 1,840,000 B). `0` restores the historical layout byte for byte.
- **The layout is self-describing, and the change is upgrade-only.** The capacity is persisted per
  table on both storage paths (multi-file metadata DTO and the single-file `TableMetadataEntry`,
  carved out of its *reserved* bytes so entry size and every field offset are unchanged). A reopened
  database decodes with the capacity its records were **written** with. This also fixed a real
  defect: before it, a table created with a non-zero capacity came back from a reopen decoding every
  inline slot as an arena offset and returning `DBNull`.
- **The overflow arena no longer opens its file once per value.** `IOverflowArena.WriteMany` appends
  a row's payloads with one `AppendBytesMultiple` call instead of one `FileOptions.WriteThrough`
  open per value — the profiler's `arena-append` call count fell from **3 per row to exactly 1**.
  Measured **1,428 → 523.51 µs/row** on that shape (**2.73×**).
- **The SQL multi-row `INSERT … VALUES` path now runs inside a storage transaction**, exactly as the
  direct batch API always has (9.65× on that shape; **523.51 → 54.26 µs/row**, cumulative
  **2,069.77 → 54.26 µs/row / 38×** with the batching and arena work).
- **`DatabaseConfig.WalDurabilityMode` now governs the table append**, so an explicit `Async` choice
  engages the append buffer with its 1 MB / 10 ms flush bounds. **The default is unchanged**
  (`FullSync`, write-through per record), so no existing database silently gains a durability
  window; with `Async`, buffered rows are lost by a process crash as well as by power loss.
- **In-place UPDATE/DELETE and deferred index maintenance** put the fixed-width fair-PK layout ahead
  of SQLite on UPDATE and DELETE (see §4.1).

### 2.2 Vector, search, and analytics (Munarium-inspired)

- **Content-verified immutable artifacts** — `ArtifactManifest`, canonical SHA-256 `artifact_id`,
  `IVerifiableIndex` with a content-addressed `Verify()`.
- **DiskANN index** — a real Vamana graph (seeded R-regular init, greedy search, robust prune α=1.2,
  medoid entry point) with `MeasureRecallAgainstExact`, tuning knobs and a per-query beam override,
  plus `CREATE VECTOR INDEX … USING DISKANN` SQL DDL.
- **Lexical stack** — classifying tokenizer, PostgreSQL-16 English stop words, word-only stemmer and
  a BM25 inverted index with positions (`SharpCoreDB.Search`).
- **Hybrid search** — BM25 and vector legs fused **by rank** (reciprocal-rank fusion), never by raw
  score (`SharpCoreDB.HybridSearch`).
- **Event sourcing** — optimistic-concurrency conditional appends
  (`TryAppendEventsAsync(expectedVersion)` → `ConditionalAppendResult`).
- **Hybrid fusion alpha** (`VectorSearchOptions.HybridFusionAlpha`) is recorded in the artifact
  manifest; wiring the weighted scorer into GraphRAG ranking is **still open** (Phase 3, partial).

### 2.3 .NET 11 / C# 15 platform

- `net11.0` only, `LangVersion=preview`, Runtime Async enabled on the core project.
- Native Zstandard compression (`ZstandardStream`) with quality presets and frame checksum.
- `SharpCoreDB.Net11` — an additive C# 15 API surface. True C# 15 union types for `BuildResult`
  remain deferred to .NET 11 GA (today it is a `record` hierarchy).

| Database | INSERT ops/s | READ ops/s | UPDATE ops/s | DELETE ops/s |
|---|---:|---:|---:|---:|
| SharpCoreDB (SQL) | 85,560 | 67,482 | 63,853 | 107,871 |
| SharpCoreDB (Direct API) | 124,976 | 139,840 | 98,421 | 235,605 |
| SharpCoreDB (StructRow) | 133,023 | 108,602 | — | — |
| SQLite | 134,662 | 87,955 | 263,040 | 342,813 |
| LiteDB | 71,143 | 13,745 | 10,173 | 14,861 |
| BLite 4.0.1 | *skipped* | *skipped* | *skipped* | *skipped* |

The three ladders are reported **separately and never as one number** — they are different routes

prints the exception and continues rather than reporting a fabricated column.


## 4. Fair-PK arms (median of 3 per phase)

The fair-PK shape is `id INTEGER PRIMARY KEY` on both engines with `WHERE id = @pk`, which is the
shape that engages the in-place fast paths, so the gap numbers below are the honest positional
statement of where v2.1 RC stands.

### 4.1 AppendOnly — `--pk`

| Arm | INSERT | READ | UPDATE | DELETE |
|---|---:|---:|---:|---:|
| SharpCoreDB legacy, plaintext | 111,923 | 74,495 | 138,399 | 263,270 |
| SharpCoreDB fixed-width, plaintext | 108,661 | 105,652 | **324,560** | **736,046** |
| SharpCoreDB fixed-width, at-rest | 109,717 | 91,981 | 251,267 | 373,616 |
| SQLite (reference) | 156,946 | 93,551 | 258,213 | 342,452 |

| Gap vs SQLite | legacy | fixed-width | fixed-width at-rest |
|---|---:|---:|---:|
| UPDATE | 1.9× behind | **0.8× (ahead)** | 1.0× |
| DELETE | 1.3× behind | **0.5× (ahead)** | 0.9× |
| INSERT | 1.4× behind | 1.4× behind | 1.4× behind |

At-rest tax on the same arm shape: INSERT 0.99×, READ 1.15×, UPDATE 1.29×, DELETE 1.97×.

### 4.2 AppendOnly pure default — `--pk-default`

No harness knobs at all (`NoEncryptMode` stays at its default `false`).

| Database | INSERT | READ | UPDATE | DELETE |
|---|---:|---:|---:|---:|
| SharpCoreDB (default config) | 96,266 | 55,533 | 79,337 | 208,722 |
| SQLite | 180,409 | 94,087 | 284,996 | 366,093 |
| gap | 1.9× | 1.7× | **3.6×** | **1.8×** |

The pure-default UPDATE gap is dominated by the documented `NoEncryptMode` mechanism (file-level
encrypt/decrypt wrappers around the resolution, point and page-cache reads even though per-record
at-rest encryption is off) — see [`benchmarks/default-config-pk.md`](benchmarks/default-config-pk.md).
DELETE improved markedly against the historical record (92,646 → 208,722 on a run whose SQLite
reference moved 389,120 → 366,093), i.e. mostly **the gap**, not the machine.

### 4.3 PageBased engine — `--pk --engine=pagebased`

| Arm | INSERT | READ | UPDATE | DELETE |
|---|---:|---:|---:|---:|
| SharpCoreDB legacy, plaintext | 158,490 | 168,801 | 26,338 | 176,230 |
| SharpCoreDB fixed-width, plaintext | 175,562 | 210,210 | 58,464 | 304,980 |

## 5. What is still behind, stated plainly

1. **INSERT on the fair-PK shape is ~1.4× behind SQLite** (1.9× on the pure default config). The
   batched multi-row shape converted to a measured win in this line; the single-row statement path
   did not. The residual is the SQL/engine path per statement plus per-value write-through
   durability, not the storage I/O — the profile is in the plan §11.
2. **PageBased UPDATE** (4.9× behind on the fixed-width layout) — instrumented, not yet fixed.
3. **Pure-default (encrypted) throughput** is 1.3–1.6× behind the `NoEncryptMode` raw-speed posture
   on every phase. `NoEncryptMode=true` remains the explicit, documented opt-out for benchmarks and
   speed-critical deployments; **the security default has not been weakened.**
4. **Gate variance:** the write-path gate passed, but this session's rep spread reached 2.08× on a
   loaded machine, so ratios below ~1.3× in a single run are not attributable.
5. **Single-file (`.scdb`) migration is one-way** for v1.x files (unchanged from v2.0, `.backup`
   preserved), and there is **no downgrade path** for the new inline-capacity layout: an older build
   reading a new file would misread its inline slots.

## 6. Upgrading

- **From 2.1.0-RC.1 / RC.2:** drop-in. No API removal; the storage change is upgrade-only and
  self-describing.
- **From 2.0.0.x (the `master` line):** the v2.1 RC packages are `net11.0` only. Existing databases
  open unchanged; new PK tables pick up the inline-capacity-16 layout.
- **From the 1.9.x line:** see [`2.0.0.0_WHAT_CHANGED.md`](2.0.0.0_WHAT_CHANGED.md) plus
  [`manual/upgrade-and-downgrade.md`](manual/upgrade-and-downgrade.md).

```bash
# Core
dotnet add package SharpCoreDB --version 2.1.0-RC.3

# Server / client and providers
dotnet add package SharpCoreDB.Server.Core --version 2.1.0-RC.3
dotnet add package SharpCoreDB.Client --version 2.1.0-RC.3
dotnet add package SharpCoreDB.Data.Provider --version 2.1.0-RC.3
dotnet add package SharpCoreDB.EntityFrameworkCore --version 2.1.0-RC.3

# Engines and extensions
dotnet add package SharpCoreDB.VectorSearch --version 2.1.0-RC.3
dotnet add package SharpCoreDB.Search --version 2.1.0-RC.3
dotnet add package SharpCoreDB.HybridSearch --version 2.1.0-RC.3
dotnet add package SharpCoreDB.Analytics --version 2.1.0-RC.3
dotnet add package SharpCoreDB.Graph --version 2.1.0-RC.3
dotnet add package SharpCoreDB.Graph.Advanced --version 2.1.0-RC.3
dotnet add package SharpCoreDB.Extensions --version 2.1.0-RC.3
```

> The v2.1 RC packages are **pre-release** versions: NuGet will not select them unless the version is
> requested explicitly (as above) or *Include prerelease* is ticked in Visual Studio.
